# 双池外联：同主题互动 + 爆款帖互动

> 本文件是外联的执行规则。所有数字（30 条、15+15、窗口、间隔）都是实战默认值，集中在账号配置中调整。
>
> **30 条是计划上限，不是必须硬刷的 KPI；错过时段、没有合格候选或出现风控，宁可少做。**

## 0. 开跑前置：详情页可达性探测（硬门）

每轮外联开始前，必须先证明「带合法 token 的详情页能正常渲染」。
**三步固定顺序，不许跳步、不许倒序。**

### 步骤 1｜先取 token，再谈探测

裸链接 `/explore/<id>`（无 `xsec_token`）**必然 300031，且与账号状态无关**。
因此「打开笔记」这个动作，必须先拿到 token 才有意义。

取 token（本账号自己的笔记）：

```text
已登录页 → network(match="user_posted", reload=true)
→ 从响应体 data.notes[].xsec_token 取任一 note_id 的 token
```

- 直接 `fetch` 该接口会 `406`（缺签名头），**只能读已发生请求的响应体**。
- token 内含 `=`，拼进 URL 时必须编码为 `%3D`。
- 探测 URL 形态：`/explore/<note_id>?xsec_token=<TOKEN>&xsec_source=pc_user`

### 步骤 2｜带 token 打开，看正文而不是看状态码

判据是**正文是否渲染**，不是 URL 是否停在 `/explore/`：

| 观察 | 判定 |
|---|---|
| 标题 + 正文 + 评论框都在 | 可达 ✅ 执行本轮 |
| 落到 `/404?...error_code=300031` | 真阻断 ❌ 走步骤 3 |
| 标题出来了但正文区空白 | 渲染未完成，等 `idle` 后再判，**不算阻断** |

### 步骤 3｜只有「带 token 仍 300031」才允许判阻断

- 确认 URL 里 `xsec_token=` 非空、且值长度正常（约 44 字符）。
- 确认 token 来自本次会话抓取的响应体，不是陈旧缓存。
- 以上都满足仍 `300031` → **真阻断**：整轮跳过，台账记 `blocked:detail_300031`，本轮 0 条，**不重试、不换号、不绕过、不找替代路径硬试**。

### 0.1 两种 300031 的鉴别（实战血泪教训）

| 成因 | 特征 | 处置 |
|---|---|---|
| A. 链接缺 `xsec_token` | URL 无 `xsec_token=` 或值为空 | **假阻断**。补 token 重开，**不算重试** |
| B. 会话/账号级封禁 | 带合法 token 同样 300031 | 真阻断。整轮跳过 |

**绝对禁止**用 `eval` 对隐藏的 `<a href="/explore/xxx">` 调 `.click()` 做探测。
XHS 个人页/首页的可见卡片是 `div`，跳转靠 SPA 路由带 token；DOM 里那个 `<a>` 是 `display:none` 的预加载节点，**href 没有 token**，点它必然裸跳 → 300031。实战中曾因此误判「账号被封」，整轮外联白废。

正确的打开方式（按优先级）：

1. 搜索结果页卡片：`a[href*="/search_result/"]` 的 href **自带 token**，真实点击即可。
2. 个人页/首页卡片：点可见卡片容器（坐标点击），**不要点隐藏 anchor**。
3. 已有 token：直接 `navigate` 带 token 的 `/explore/<id>?xsec_token=...`。

### 0.2 误判的代价

实战曾观察到 300031 后未核验 token 即判「会话级封禁」，当轮 0 条收工；随后用带 token 链接实测，**同一账号同一篇笔记正常渲染正文、评论框与全部评论**，证明是假阻断。

一条铁律：**在没有 token 的情况下，任何 300031 都不构成封禁证据。**
下沉一层：账号风控是服务端按账号/会话判的，换浏览器（含 Playwright）不能改变结论，**换工具解决不了 token 问题**。

## 1. 每日计划上限

| 类型 | 计划上限 | 目的 |
|---|---:|---|
| 同主题互动 | 15 | 进入垂直内容场，建立同行与潜在用户认知 |
| 爆款帖互动 | 15 | 进入公共高流量场，获得更多曝光和主页回流 |
| 合计 | 30 | 计划上限；遇风控、时间不足或候选不合格可提前停止，不为凑数灌水 |

以上数字都不是必须完成的 KPI。没有合格帖子、时间不足、主页承接不合格或出现账号风险时，允许只做少量或 0 条。

两类必须穿插执行，不允许先集中做完一类。

执行后的硬约束：

- 成功数不得超过 30，单池不得超过 15。
- 单次执行最多成功 2 条，推荐“同主题 1 条 + 爆款 1 条”。
- 任一时段没有合格候选就跳过，不拿无关帖、0 评论荒地帖或争议帖补数。

## 2. 时间与节奏（默认：晚间是流量高峰，按账号数据调整）

### 2.0 现行窗口口径

> 多数账号的实测强时段在晚间。窗口因此拆成**同日多段**并给高峰段优先权，
> 而不是「23:30 一刀切」。具体窗口以配置 `scheduling` 为准。

| 段 | 时间 | 性质 |
|---|---|---|
| 深夜尾峰 | `00:00–02:00` | 晚间高峰跨零点的延续，**允许执行**，计入新自然日配额 |
| 静默窗口 | `02:00–09:30` | **不发起任何外联留言或关注动作**；只允许记 `skipped` |
| 白天常规 | `09:30–18:00` | 允许执行，低优先 |
| 晚间主高峰 | `18:00–24:00` | **优先执行**，每日计划位 60% 落在高峰段（含深夜尾峰） |

- **运营日 = 自然日**，配额仍按 `at.date()` 归属。因此窗口拆成**同日多段**，
  不写 `09:30–02:00` 这种跨日窗口（`parse_window` 会拒绝），避免一个晚间场次被劈成两个配额日。
- 晚间场允许跨零点连续执行：23:50 留言、00:10 继续回扫/留言是同一场次，**不记 `skipped`、
  不算窗口外补量**；00:10 的留言计入 11-12 的配额。
- `peak_share: 0.6` 只影响**计划位分布**，不是 KPI；30 条仍是每日计划上限，不是必须刷满的量。
- 台账每条成功记录带 `window_tag`（`peak` / `regular` / `off_window`），用于后续复盘
  晚间高峰是否真的带来更多主页访客与关注；不预设因果结论。
- 建议把外联优先时段与账号实测的发布强时段对齐；未验证的时段先跑数据再判断。

### 2.0.1 执行节奏（其余硬约束一律不变）

- 任意滚动 60 分钟最多 3 条（不是按整点小时重新计数；排程器也按滚动窗口校验）。
- 相邻两条成功评论之间至少 10 分钟；不要把 10 分钟当成催速度的目标。
- 单次连续最多 1–2 条，单轮最多成功 2 条。
- 同一天的时间分布要随机，不要每天同一套时间；但**优先落在高峰段**。
- 两类交替，不连发同一类。
- 同一作者 7 天内不重复互动。
- 同一句话 7 天内不复用。
- 静默窗口内、候选不合格或出现风控时直接记 `skipped`；任何时段都不为凑计划上限补量。

### 2.1 停留与批量打开（硬规则，不许简化）

**禁止「打开即评论」。** 打开笔记就立刻留言是最容易被判机器行为的动作，必须拆成三段：

```text
① 批量打开：同主题 1–3 篇 + 爆款 1–2 篇，同时开在多个标签页
② 整体停留 30–60 秒：轮着滚动、展开评论区、读至少 3 条已有评论
③ 逐个留言：每篇再单独停留 5–10 秒，然后写评论、发送
```

要点：

- **停留要有行为痕迹**，滚动、展开评论、停在评论区；不能只挂页面不动，也不能打开就关。
- 留言顺序与打开顺序不一致，别按标签页顺序挨个发。
- 两条成功留言之间至少间隔 **10 分钟**，实际建议留到 12 分钟以上，用真实等待。
- 一轮（单次执行）最多成功 **2 条**；先处理完一条并回读，再处理下一条，不做一次性连发。
- 批量打开后如果某篇内容不适合评论（如争议、求助、无关），直接关掉不发，不硬凑。

批量打开 3–5 篇与“每次只处理一条”并不冲突：前者是阅读和停留，后者是发送纪律。禁止同时开十几个标签页连续灌评论。

实际执行时先生成计划，再按计划行动：

```bash
python3 <skill-dir>/scripts/plan_outreach.py --config xiaohongshu-ops.yaml --date YYYY-MM-DD
```

如果用户没有指定日期，使用账号配置中的时区生成“今天”的计划。

## 3. 选帖

### 同主题

优先级：

1. 与账号主线直接相关。
2. 最近 24–72 小时。
3. 优先“关键词 + 地区/本地实名讨论”，比泛流量帖更有同频感。
4. 内容质量高，评论区至少有 1 条真实讨论。
5. 作者不是营销号或批量号。
6. 评论不会被完全淹没。

0 评论的“荒地帖”不用于同主题外联。补首评是自家笔记的任务，不是外联任务。

搜索词围绕账号支柱配置，不要只搜一个词。

### 爆款

优先级：

1. 流量大。
2. 近期仍活跃。
3. 评论区有可被看见的位置。
4. 内容本身值得欣赏，而不是靠争议或骂战。
5. 避开政治、灾难、疾病求助、网暴、悲剧当事人等高风险场景。
6. 评论数千条且最新评论也很难被看到时，降低优先级，不为了“流量大”硬挤。

不要只挑最大账号。大号评论区可能完全看不到你的留言，优先“高流量但仍有可见讨论位置”的内容。

## 4. 评论情绪模型

第一目标不是“提问引流”，而是让对方和围观者感到：

- 你是被内容吸引过来的。
- 你认真看了。
- 你和作者在某些价值判断上同频。
- 你给出了具体、真实的情绪回应。

### 核心情绪

- 赞扬
- 赞赏
- 欣赏
- 共鸣
- 共同关注
- 同频感
- 被内容打动

### 问句比例

- 30 条日计划中，**至少 25 条不带问句，最多 5 条带问句（≤16.7%）**。
- 同主题 15 条中最多 3 条带轻问句（≤20%）。
- 爆款 15 条中最多 2 条带问句（≤13.3%）。
- 2 条连着的评论不允许都带问句。
- 每条最多一个问句，而且问句必须放在最后一句；先追问再补陈述视为不合格。
- 只有原帖里有明显未展开、且你确实能接着聊的具体细节时才提问；没有问题就不问。
- 评论审核按批次大小四舍五入到允许条数，例如 5 条爆款最多 1 条问句；不得因为某个小批次没有问句，就在下个批次连续补问。

## 5. 评论写法

所有评论都必须满足：

1. 至少有一个贴住原帖的具体细节，不能只说“写得好”“有共鸣”。
2. 让作者能自然感到“你是被这篇内容吸引过来的、和他同频”，可用赞赏、认同、共同关注或“正好也是我关心的”等表达。

可选增强（不能替代上面两项）：

- 补充一个真实、轻量的观察；
- 保留口语感，不写成小作文；
- 不主动展示自己的账号、职业或业务。

默认长度 **≤30 个汉字（硬上限，配置 `tone.max_chars` 可调）**，最多 2 句；长度按汉字计，标点不计。不做长评说教。不同评论要换开头和句式，避免每条都以“这个角度”“看到这段”“我也”开头。短到只有一句具体反馈也可以，硬凑字数反而模板感重。

### 5.1 轻夸模式（可选，配置 `tone.light_praise` 开关）

**场景**：随机访问（尤其爆款池刷到）的女性博主，内容是日常/生活/颜值向，没有可接的具体细节，硬写细节反而刻意。此时允许只留一句短夸，**不写长评**。

规则：

- 台账与质检用 `style: light_praise` 标记（`outreach_ledger.py record --style light_praise`）。
- **1 句、≤15 字**；不带问句、不带 CTA、不带外链，全局禁止项照常生效。
- 只夸**状态、气质、善意**（如「人美心善」「状态真好，看着舒服」「笑起来真治愈」「气质在线」「好有生活气息」）；不评价身材长相细节、不越界不暧昧、不编造细节。
- 每日轻夸 ≤ **10 条**，且不得全部用轻夸凑量——至少 20/30 条仍走“细节 + 同频”正评。
- 连续两条不得都是轻夸；`lint_comments.py` 会硬拦（consecutive_light_praise / light_praise_daily）。
- 轻夸对 `lint_comments.py` 跳过「具体细节/同频/赞扬词」硬校验，但导流词、长度（15 字）、问句、句数仍然硬拦。
- 同一句 7 天冷却、同作者 7 天冷却，沿用 `cooldown` 现有口径。

推荐句式（可换着用，勿复用同一句）：

- “人美心善”
- “状态真好，看着舒服”
- “笑起来真治愈”
- “气质在线”
- “好有生活气息”

禁止：

- 对男性博主照搬同一套外貌向夸法（场景仅限女性博主的日常/生活向内容）
- 评价身材、穿着细节或任何越界表达
- 用轻夸回复争议、求助、悲剧类内容

推荐句式（正评，≤30 汉字，可换着用，勿复用同一句）：

- “____这段把关键处讲透了，和我的判断一致。”
- “被____吸引进来了，这个细节一看就花了心思。”
- “之前没往这层想，你这个讲法很清楚。”
- “这个角度很少见，看完有共鸣。”
- “原来不只我这么理解，说到心里了。”
- “退休年限这段讲得实在，我也一直在关注。”

禁止：

- “求关注、互关、看我主页、私信我、主页有惊喜”
- “我也做这个，来看看我的”
- “你怎么看、你遇到过吗”每一条都问
- 复制同一句评论
- 大段说教
- 贬低作者或其他评论者
- 蹭灾难、疾病、争议当事人
- 外链、联系方式、二维码
- 假装认识作者或编造经历
- 展示职业、履历、项目或业务能力来证明自己专业
- 每条都塞“我也”“共鸣”“同频”等同款词，造成模板感

### 5.2 AI 身份追问应对

**场景**：在外联评论或自家笔记评论区，有人问“你是不是 AI / 机器人 / 真人吗”。

规则：

- **大胆承认**：不否认、不装真人、不回避、不拉扯、不解释技术细节。
- 承认后紧接着回一句固定话术（配置 `tone.ai_admission.reply_text` 自定义，保持在字数上限内）。
- 只用这一句，不展开、不接第二轮解释；对方继续追问就停，不再回。
- 这是被追问场景的应对，**不用于主动留言**，不写进外联评论批次。
- 记台账时按 `own_comments` 回复流程记录，备注 `ai_admission`。

## 6. 评论质检

发布前使用：

```bash
python3 <skill-dir>/scripts/lint_comments.py --config xiaohongshu-ops.yaml --input comments.json
```

检查项：

- 是否有具体指向原帖
- 是否有正向情绪
- 是否有同频感
- 问句比例
- 单个问句是否位于最后一句
- 长度和句数
- 是否含外链/联系方式/导流词
- 是否重复开头或重复句子

### 6.1 发送前后硬校验

1. **先核对账号**：页面登录账号必须与配置账号一致；不一致立即停止，不代发。
2. **单写者**：同一账号同一时间只允许一个 Agent/任务执行外联；发送前先查台账和当前页面，避免并行会话重复评论。
3. **回复绑定**：点“回复”后必须确认输入框已打开且父容器包含目标评论；出现 `not found`、空引用、绑定不明，立即停止，不得退化成笔记顶层评论。
4. **发送按钮实时定位**：每次发送前重新取提交按钮位置；禁止复用硬编码坐标。
5. **成功判定**：不能只看“点击成功”或 toast。至少满足“评论计数 +1、刷新后仍 +1、输入框清空”；评论区为虚拟列表、看不到新楼层时，以计数持久化 + 发帖请求成功作为辅助证据，并标注“楼层未可见”。
6. **失败不重发**：超时、页面结构异常或状态不明时先刷新核验；确认未发出才允许重试一次。
7. **台账证据**：成功记录必须带 `--round-id`；一个 round 最多 2 条成功。核验后仍无法确认结果时记 `--result skipped`，不得把“不确定”写成成功。

## 7. 主页承接

外联只负责把人带到主页，关注取决于主页。

每次提高外联权重时，同时检查：

- 头像是否像真人账号
- 昵称是否易记
- 简介 3 秒内说清“帮谁、提供什么、为什么值得关注”
- 置顶是否放最强 2 条
- 前 6 条内容是否在同一主线
- 最新内容是否能证明账号持续更新

如果主页承接不合格，先修主页，不要把外联量继续拉高。

## 8. 评估指标

不能只看“发了多少条”。至少记录：

- 发出数
- 成功数
- 评论获赞数
- 作者或用户回复数
- 24h 主页访客变化
- 24h 关注变化
- 每百条外联带来的主页访客和关注增量（近似归因）
- 各评论风格的表现差异

若连续 7 天高外联量但主页访客和关注无明显变化，先降量并修主页承接，不盲目加量。

## 9. 风控停止条件

出现任一情况立即停止当天外联：

- 验证码
- 操作频繁
- 登录失效
- 评论连续失败
- 被限制评论
- 陌生人私信限制
- 账号收到风险提示
- 评论区加载异常或页面结构异常

不要绕过验证码，不要用不同账号规避限制。

## 10. 关注回扫（可选，配置 `follow_back` 开关）

> **流程**：每次留言成功 → 记下留言位置（`note_url` + `author_id`）→ 下一轮开头先回到那个位置关注博主 → 再做本轮留言。

### 10.1 为什么要回扫

留言是"我把话递过去"，关注是"我留下来"。只留言不关注，对方收到通知点进主页的概率低；
留言后隔一轮再关注，动作分散在不同时间点，不像机器连招，也给了真实停留痕迹。

### 10.2 固定顺序（不许跳步、不许倒序）

```text
每轮外联：
  ① gate      → 本轮能不能关注、能关注几个（配额 / 窗口 / 间隔）
  ② pending   → 取待关注博主（按留言时间【降序】：先补最近一轮）
  ③ 回到那条笔记 → 点作者昵称进主页 → 点关注
     （顺带核验上一轮留言是否还在：被删/被吞要记下来）
  ④ record    → 回写 done / failed / skipped
  ⑤ 本轮留言  → 选帖 → 批量打开 → 停留 → 留言（回到第 3 节正常流程）
```

**关注必须在留言之前**，不是之后。这样每一轮都是"先补上轮的人情，再开新的场"。

### 10.3 硬约束（比留言更严）

| 约束 | 值 | 理由 |
|---|---:|---|
| 每日关注上限 | `daily_max: 10` | 关注比留言更容易触发风控 |
| 且不超过当日留言成功数 | 双重取小 | 留言都没发出去却关注一堆 = 明显机器行为 |
| 单轮最多 | 2 | 与"单轮最多 2 条留言"对齐 |
| 相邻关注间隔 | ≥10 分钟 | 与留言同纪律 |
| 回扫窗口 | 留言后 24 小时内 | 只补「上一轮」，不翻旧账 |
| 自己 | 跳过 | 不关注自己 |
| 活跃窗口 | `00:00–02:00` / `09:30–24:00` | 与留言一致；`02:00–09:30` 静默 |
| 留言数上限口径 | **滚动 24h 成功留言数** | 按自然日计会在跨零点时把昨晚刚留言的博主永久挡住 |

### 10.4 失败与风控

- **失败不重试**：`failed` 直接出队，下一轮不再重复关注同一人，避免反复打扰。
- **风控信号即停**：备注里出现「操作频繁 / 验证码 / 登录失效 / 风险提示 / 被限制」，
  记 `skipped` 并 **停止当天全部关注**（`on_risk_signal: stop`），不是只停这一条。
- **超时不追**：留言超过 24 小时自动出队（状态 `expired`），不补关注。

### 10.5 命令

```bash
# 1. 本轮能不能关注、能关注几个
python3 <skill-dir>/scripts/follow_queue.py gate --config xiaohongshu-ops.yaml

# 2. 取待关注队列
python3 <skill-dir>/scripts/follow_queue.py pending --config xiaohongshu-ops.yaml --limit 2

# 3. 回写结果（备注里带风控信号会自动置 stop_today）
python3 <skill-dir>/scripts/follow_queue.py record --config xiaohongshu-ops.yaml \
  --author-id <id> --result done --note ""

# 4. 统计
python3 <skill-dir>/scripts/follow_queue.py stats --config xiaohongshu-ops.yaml
```

`gate` 退出码非 0 = 本轮不关注，直接进留言环节，不要硬凑。

### 10.6 执行边界

关注是对外可见动作，**必须当前任务明确授权**才执行。脚本本身只做队列与记账，
不发起任何关注动作；实际点击由人工或已授权的浏览器流程完成。

## 12. 点赞用户感谢私信（可选，配置 `dm_thanks` 开关）

> 平台不暴露收藏者名单（只有总数），因此触达对象改为**可见的点赞用户**，话术去营销化。
> 「专业提供 xx 服务」这类明确推销**不得照发**（违反 no_profile_cta 与平台营销风控）。

### 12.1 对象与来源

- 只给**给我的笔记点过赞**的用户发；来源用消息中心的「赞和收藏」通知，取近期点赞者。
- 收藏者、纯浏览者一律不触达（拿不到名单，也不该触达）。

### 12.2 硬约束

| 约束 | 值 |
|---|---|
| 每日上限 | 3 条 |
| 单次执行 | 最多 2 条 |
| 相邻间隔 | ≥30 分钟 |
| 逐条批准 | 每条发送前把昵称+话术列给用户确认，未确认不发 |
| 话术 | 只从 `tone.dm_thanks.template_pool` 选，7 天内不复用同一句 |
| 同一作者 | 30 天冷却 |
| 禁止内容 | 服务推销、导流词、「交个朋友」类拉近话术、问需求、外链 |

### 12.3 话术池（≤30 汉字，去营销化）

- “谢谢支持，这条的补充清单我更新在评论区置顶了”
- “谢谢喜欢，这类问题我每周都会更新一篇，可以常来”
- “谢谢认可，有具体疑问欢迎在评论区留言，我看到就回”

### 12.4 风控

- 出现「陌生人私信限制 / 操作频繁 / 验证码」立即停止当天全部私信，按 §9 处置。
- 每条成功后在台账记 `kind: dm_thanks`，备注用户确认时间。

## 13. 自动运行边界

- 本 Skill 默认只提供人工或当前任务触发的执行规则，不自动创建、恢复或改写任何定时任务。
- 恢复任何定时任务前，必须先由用户明确授权，并把旧自动化提示词迁移到本 Skill 的统一规则；未迁移的旧提示词只能作为历史资料。
